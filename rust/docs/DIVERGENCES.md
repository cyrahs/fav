# Intentional differences from the Python baseline

Every place where the Rust build deliberately behaves differently from Python at `rust/BASELINE`, and every
Python bug found while porting (copied or fixed). Add an entry in the PR that introduces the difference.
The independent review checks that nothing differs without an entry here.

Kinds:

- **dropped**: legacy behaviour the plan removes (SQLite-dialect translation, CookieCloud cleanup,
  old-field startup migrations, tqdm bars).
- **mechanism**: same observable behaviour, different machinery (for example grammers instead of Telethon).
- **observable**: a user, the front end, an API client or stored data can tell the difference.
- **python-bug**: a bug found in Python; say whether Rust copies it or fixes it, and why.

| D3 | WP0 (for WP2) | python-bug | APScheduler 3.11 `CronTrigger` can return the previous fire time again on a DST fall-back (`15 1 * * *` in America/New_York repeats 2026-11-01 01:15-05:00, `get_next_fire_time(T, later)` returns `T`), so the scheduler's run-time loop would not advance | Rust fixes it: the next fire time is always strictly after the previous one; the affected cases in `rust/goldens/scheduler/cron_next_fire.json` are the ones whose `fires` repeat a value | A hang is not behaviour worth copying. It needs a DST zone in `TZ`; the fav manifest sets none (the SOPS env secret could), so production is probably unaffected. Max can overrule | Review of #133 |

| D4 | WP1 | dropped | `ensure_table_sync()` deletes the retired `cookiecloud` row and moves `tikhub_token`/`tikhub_api_url` out of `web.wechat` into `services.tikhub` at every start | Neither migration runs; a leftover `cookiecloud` row or `web.wechat.tikhub_*` field is ignored when reading (unknown sections and extra fields are skipped, as in Python) | Plan non-goal (old-field startup migrations): Python has run both at every start since they were added, so the production rows are already migrated. | D6 | WP1 | mechanism | Each source creates its tables the first time it runs (`_ensure_table()`), adding later columns with `ALTER TABLE` | `fav-db`'s `schema.sql` creates every table, every later column and every index at startup, under an advisory lock, in Python's three blocks (tables, added columns, indexes). On an empty database the result is identical to Python's (`rust/parity/schema.txt`, compared catalog line by catalog line instead of a `pg_dump` diff) | One script instead of 20 places; a database the Python code created is brought up to date the same way, including tables of sources that never ran | Plan, 2026-11-09 |
| D7 | WP1 | observable | `str(ValidationError)` is pydantic's long text with input values and a docs URL per error | The `Display` text is shorter: `N validation errors for Model`, then `loc` and `msg [type=...]` per error. | D8 | WP1 | observable | `json.loads` accepts integers of any size and strings with lone surrogates (`"\ud800"`) | `fav_core::pyjson::loads` refuses integers outside `i128` ("Integer out of range") and lone surrogates ("Lone surrogate escape"); Rust strings cannot hold a lone surrogate | Neither occurs in anything fav stores or receives; refusing is louder than corrupting | Plan, 2026-11-09 |
| D9 | WP1 | dropped | `src/tool/database.py` accepts SQLite-flavoured SQL (`?`, `INSERT OR IGNORE`, `PRAGMA table_info`) and translates it, including several statements in one string (`query_db_multi`) | Native PostgreSQL with `$n` placeholders, one statement per `Statement`; `query_batch`, `query_transaction` and `insert_batch` keep Python's chunking and its argument and batch-result messages. Waived: `test_query_db_multi_rewrites_sql` | Plan, 2026-11-09 |

If the server's zone ever changes, set it in an `after_connect` hook | WP1 PR; Max can overrule |
