# Intentional differences from the Python baseline

Every place where the Rust build deliberately behaves differently from Python at `rust/BASELINE`, and every
Python bug found while porting (copied or fixed). Add an entry in the PR that introduces the difference.
The independent review checks that nothing differs without an entry here.

Kinds:

- **dropped**: legacy behaviour the plan removes (SQLite-dialect translation, CookieCloud cleanup,
  old-field startup migrations, tqdm bars).
- **mechanism**: same observable behaviour, different machinery (for example grammers instead of Telethon).
- **observable**: a user, the front end, an API client or stored data can tell the difference.
- **python-bug**: a bug found in Python; say whether Rust copies it or fixes it, and why.

| D3 | WP0 (for WP2) | python-bug | APScheduler 3.11 `CronTrigger` can return the previous fire time again on a DST fall-back (`15 1 * * *` in America/New_York repeats 2026-11-01 01:15-05:00, `get_next_fire_time(T, later)` returns `T`), so the scheduler's run-time loop would not advance | Rust fixes it: the next fire time is always strictly after the previous one; the affected cases in `rust/goldens/scheduler/cron_next_fire.json` are the ones whose `fires` repeat a value | A hang is not behaviour worth copying. | D6 | WP1 | mechanism | Each source creates its tables the first time it runs (`_ensure_table()`), adding later columns with `ALTER TABLE` | `fav-db`'s `schema.sql` creates every table, every later column and every index at startup, under an advisory lock, in Python's three blocks (tables, added columns, indexes). | D12 | WP2 | dropped | `ensure_notifications_table()` runs two backfills at every start: `status = 'read'` rows get `delivery_status = 'delivered'`, and old worker `job_failed:` rows with `scope = 'item'` get `scope = 'job'` | Neither runs; `ensure_schema` creates the columns and the index only | Plan non-goal (old-field startup migrations): both have run at every Python start since they were added, so production rows are already backfilled. `test_ensure_notifications_table_runs_schema_migration` checks the resulting columns | Plan, 2026-11-09 |
| D13 | WP2 | observable | APScheduler's cron parser takes any Unicode digit (`\d`) and Python's case-insensitive `[a-z]` letters; numbers are unbounded until a range check refuses them. Zones come from the system zoneinfo or the `tzdata` package. Due-ness compares aware datetimes of one zone by wall time | Numbers and names are ASCII only; a number beyond `i64` is refused with `Number too large in cron expression: N`. Zones come from `chrono-tz`'s bundled tzdata. The scheduler decides due-ness on instants, so in a fall-back hour a run is due when its instant has passed | Stored cron settings are ASCII (the UI writes them); tzdata versions can differ by a release either way. Comparing wall times in a repeated hour would start a run an hour early or late | WP2 PR; Max can overrule |
| D14 | WP2 | python-bug | `_consume_control_requests` has no error handling: one database error while claiming or executing kills the consumer task for the life of the process, and the claimed request stays `running` until the next start marks it interrupted | Rust fixes it: the error is logged (`Control request loop failed: ...`), a request it had claimed is marked failed (`Failed to record control request N: ...` if that fails too), and the loop polls again after the poll interval | Manual triggers silently stop working until a restart; nothing depends on that | WP2 PR; Max can overrule |
| D15 | WP2 | python-bug | Each job's runner closes over the `ScheduledJob` built at startup, so a later change to a job's `notify` toggle does not reach its runs until the worker restarts; which jobs are enabled and their cron are re-read | Rust copies it: runners are built once from the startup snapshot, enablement and triggers are re-read per control request and on every settings change | Harmless and visible only until a restart; fixing it changes what a run reports mid-session | WP2 PR; Max can overrule |
| D16 | WP2 | observable | At shutdown the consumers are cancelled, `scheduler.shutdown(wait=False)` returns at once and the pool is closed; a scheduled run still in flight is cancelled by `asyncio.run`'s teardown after the pool is gone, so its `control_requests` row and failure notification are usually not written (the next start marks the row interrupted) | Tasks stop cooperatively on the stop flag. A run in flight is cut short there (`CancelledError`, cancelled) and records its outcome; the scheduler waits for the runs it started, and only then is the pool closed | A run cut short by a deploy should say so; the visible difference is a `cancelled` row instead of an `interrupted` one on the next start | WP2 PR; Max can overrule |
| D17 | WP2 | observable (transitional) | Every enabled source has a runner | Sources register with `fav_sources::registry()` as their work package lands. Until then an unported source is not scheduled, a control request for it is rejected (`Runner unavailable for job: X`) and `fav trigger X` exits with that message | The Rust build is never deployed before every source is ported (WP18 checks the registry is complete) | Plan, 2026-11-09 |
| D18 | WP2 | mechanism | httpx exception class names in errors (`Telegram Bot API request failed: ConnectTimeout`); httpx has separate connect, read, write and pool timeouts | `fav_net::httpx_error_class` maps reqwest errors onto httpx's names (timeout during connect: `ConnectTimeout`, other timeouts: `ReadTimeout`, connect: `ConnectError`, body: `ReadError`, decode: `DecodingError`, redirect: `TooManyRedirects`, else `RemoteProtocolError`). reqwest has no write timeout; the total and connect timeouts are set | reqwest does not expose httpx's error taxonomy; the names only reach logs and notification text | WP2 PR; Max can overrule |
| D19 | WP2 | mechanism | `python run.py` / `python run.py --trigger X`; after each job `malloc_trim(0)` returns freed heap to the system; `log.exception` adds a traceback | `fav worker` / `fav trigger X` with the same exit behaviour (`SystemExit` messages on stderr, status 1). No `malloc_trim` (it needs `unsafe` FFI, which the workspace forbids; WP18's memory benchmark decides whether an allocator setting is needed). `Job failed: NAME` and `Invalid cron ...` are followed by the error's formatted chain instead of a traceback (D10).
