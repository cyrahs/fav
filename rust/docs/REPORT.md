# fav Rust rewrite: final report (WP18)

Facts and numbers for the planning thread's report to Max. Branch `rust`, Python baseline `67609f6`
(`rust/BASELINE`). Everything here was measured in a Claude Code cloud sandbox on 2026-11-10 unless it says
otherwise. Nothing was deployed, published or pushed outside the `rust` branch.

## Summary

- All 13 Python jobs, 44 API routes and 18 MCP tools exist in the Rust build, checked by tests against
  Python's own lists (`JOB_SPECS` names, schedules and settings sections; the post-link kinds; the routes and
  tools from the OpenAPI and MCP contracts).
- Test parity: 1074 Python test functions at the baseline, 1065 ported, 9 waived, 0 pending. 1499 Rust tests
  pass, none ignored.
- Level 2 (production data replayed read-only): 2365 of 2367 GET and read-only MCP responses identical between
  the Python and Rust APIs; the 2 others are explained below. Azur Lane manifests regenerated from the data are
  byte-identical to production's in both implementations.
- Level 3 (capped live run, anonymous sources): Jandan, Kemono, BD2 and Nikke work end to end. Stella Sora could
  not be reached from the sandbox by either implementation. **Hanime1 fails in Rust only**: Cloudflare answers the
  Rust client 403 where Python's client gets 200 from the same network (D182). This blocks running Hanime1 on the
  Rust build until it is fixed.
- Memory (same machine, same data, same load): Rust 24 MiB idle against Python's 327 MiB (three processes);
  peak under load 264 against 397 MiB; settled after load 76 against 387 MiB. jemalloc is the allocator, chosen
  by this measurement.
- Image: 643 MB compressed (2.30 GB unpacked); the binary is 45.7 MB. Built locally only.
- `main` has no commits after `67609f6`: nothing to catch up as of 2026-11-10.

## Level 2 replay

Conditions (Max's approval of 2026-11-10) and how they were met:

- Export read-only through the k8s_ops MCP `pods_exec` in the production fav pod, with `SELECT`/`COPY ... TO
  STDOUT` only. Nothing was written to production. The Rust binary never connected to the production database;
  both APIs ran against a temporary local PostgreSQL database.
- Tables and columns were listed before the dump. `site_sessions` and `wechat_account_state`: schema only, no
  rows. `app_settings`: the secret fields (`bot_token`, `token`, `api_hash`, `cookiecloud`, `nga_cookiecloud`)
  replaced inside the pod before the data left it, and checked afterwards to be masked in every row. Also masked
  in the pod: `rednote.xsec_token`; `wechat_media_queue` `context_token`, `encrypt_query_param`, `aes_key`,
  `owner_token`; `telegram_media_queue.owner_token`. Proxy settings carried no credentials. Four
  production-only tables not in the baseline schema (`tx`, `wechat`, `wechat_media_queue`,
  `wechat_account_state`) were not loaded.
- Manifests: the BD2 and Nikke manifest JSON files (592 files, hashes checked) were copied read-only; no asset
  files.
- **Deleted after the comparison**: the dump and its decoded chunks, the temporary databases (`fav_l2`, and
  `fav_bench` cloned from it for the benchmark), the copied manifests, the regenerated manifests and both
  replay outputs. Only the per-endpoint counts and diff paths below were kept.

Results:

- All 41 loaded tables have the production row counts.
- 2367 requests: all 28 JSON GET routes of the Python app (25 under `/api/v2`, `/healthz`, `/readyz`, `/openapi.json`) (the `/docs` and `/redoc` pages, icons and static
  files not compared), with list, detail and filter variants (921 Azur Lane characters and
  ship details, 210 Nikke and 91 BD2 details, archive searches per source, settings sections, jobs and job
  requests, credentials, Hanime1 seeds/authors/videos, Live2D model reads), plus 56 MCP tool calls covering 11 of
  the 12 read-only tools, and `tools/list`. `get_runtime` was not compared: it reports the running process
  (versions, commit, start time), which differ by construction.
- 2365 identical. `/openapi.json` is equal once key order inside a schema object is ignored (D29). `/readyz`
  differed in the first run because the Python API's Hanime1 deep check fetched live watch pages (see the note
  below) while the Rust one was offline; with both offline the answers are identical.
- Manifests: Azur Lane regenerated by Python and by Rust from the exported data, both byte-identical to
  production for the 903 active characters (76 production directories belong to inactive characters and are
  not regenerated by either). BD2 and Nikke manifests cannot be regenerated from the database alone (the crawl
  builds them from fetched page JSON and downloaded blobs), so the copied files were served instead and both APIs
  read them identically. Asset availability flags were false on both sides, as no asset files were copied.
- Deviation from "no external requests": in the first replay run the Python API's `/readyz` Hanime1 check made
  live requests to hanime1.me (3 anonymous watch pages per probe, probed once or twice) because only the
  upper-case proxy variables had been pointed at a dead proxy. The second run blocked every proxy variable. No
  account-bound site and no production service was contacted.

## Level 3 capped live smoke

One run per source, from the sandbox, into a temporary directory and a fresh local database (no production
data). Items were capped by seeding the local database so that only the newest few items counted as new; BD2 and
Nikke ran their single-character download, Stella Sora a three-file cap, Hanime1 parse only. The crawlers' own
pacing applied (Kemono 1 s per request, the GameKee rate limiters), plus 2-3 s between harness requests. The
harness was scratch code and is not in the repository; the database and files were deleted afterwards.

- Jandan: passed (above).
- Kemono: passed. The first configured creator had no posts on the mirror; the second was used.
- BD2, Nikke: passed.
- Stella Sora: `GET /wiki/Characters` answered 403 with Miraheze's "Checking your connection" page, for the
  Rust client and for the Python baseline alike. Not a Rust defect; untested live.
- Hanime1: Rust's ranking page request answered 403 twice and a watch page 403 once; the Python baseline's
  ranking request from the same sandbox minutes later answered 200 with 41 ids. Both go out through the
  sandbox's TLS-terminating egress proxy. A local capture shows the same header values except
  `Accept-Encoding` spacing, with Rust's header names lowercase, `Host` last and no `Connection: keep-alive`.
  Switching to title-case names alone still got 403, and the experiment was reverted. Recorded as D182.

## Memory benchmark

Setup: the same sandbox, the same local PostgreSQL database (a copy of the level 2 data, so production-sized
tables), the same collection directory (the regenerated game manifests), every job's schedule parked so nothing
ran on its own. Load, identical for both:

1. start, 60 s settle, 30 s idle;
2. API reads: 3 rounds of the list and sidebar endpoints for Azur Lane, Nikke and BD2, archive lists, job
   requests, settings and skin updates, plus 60 Azur Lane character details and ship details and 40 Nikke
   details (summary caches included);
3. 20 s pause;
4. a worker run: `POST /api/v2/job-requests {"target": "kemono"}` against a local fake Kemono (2 creators,
   120 posts, 480 files of 256 KiB, 120 MiB), polled to completion;
5. 30 s after.

RSS sampled every 0.25 s from `/proc` over the whole process tree: Python's supervisor (`python -m
src.service`), worker (`run.py`) and API (`python -m src.api`); Rust's single `fav serve` process (D1).

Results in MiB (round 2; round 1 in brackets):

| Python supervisor | 42.9 | 42.9 | 42.9 | 42.9 | 42.9 |
| Python API | 158.4 | 229.1 | 214.6 | 214.6 | 214.6 |
| Python worker | 125.2 | 125.2 | 125.2 | 129.5 | 129.0 |

- Allocator: jemalloc (`tikv-jemallocator`, the binary's global allocator). glibc kept its peak forever and
  varied between rounds (281 and 356 MiB); `arena_max=2` helped but stayed at 185 MiB; mimalloc started higher
  (37 MiB) and settled at 152 MiB; jemalloc settled lowest (75-76 MiB) with an idle cost of about 1.5 MiB.
  Python's `malloc_trim` call after each job has no safe counterpart (D19); jemalloc returns freed memory
  without it.
- Speed (same rounds): startup to `/healthz` 0.5 s against 1.5-2.0 s; the API load took 18.5-20.9 s against
  54.4-56.7 s; the worker run 1-2 s against 2.1-3.1 s.
- Production reference (Python, 2026-11-09): worker 365 MiB, API 126 MiB, supervisor 35 MiB. The production
  worker is larger than the benchmark's because real runs (Azur Lane, Bilibili, Telegram) grow it; the
  benchmark's worker run is a small Kemono job, the same for both builds.
- Not measured: `fav api` and `fav worker` as separate processes (the deployment would run `fav serve`).

## Image

`rust/Dockerfile`, multi-stage (Node front-end build, Rust release build, a uv stage that resolves yt-dlp and
gallery-dl from the root `uv.lock`, the runtime on `python:3.12-slim-trixie`). The runtime carries the `fav`
binary, yt-dlp, gallery-dl, ffmpeg, Playwright's Chromium at its registry path (`/ms-playwright`), TigerVNC's
`Xvnc`, tini and the built front end; the build runs `fav --version`, `fav nikke-layers --help` and each tool's
version check, plus a headless Chromium launch on amd64.

- Size: 643 MB compressed content, 2.30 GB unpacked on disk. Of that, Chromium and its libraries: 646 MB
  (`/ms-playwright`), the downloaders' virtualenv 35 MB, the binary 45.7 MB.
- Built locally in the sandbox only (with a sandbox-only wrapper adding the egress proxy's CA); never pushed,
  no workflow changed or dispatched. The Python image was not built for comparison.

## Choices for Max

These differences are deliberate copies or calls that Max may want to reverse; everything else in the table
below follows the plan or fixes a Python bug.

- **D97 (BD2 `isdigit()` then `int()`)**: Rust copies Python's bug: a superscript digit in a BD2 manifest or
  tree row answers 500 on the list, sidebar or detail, and fails the crawl. NIKKE's copy of the same pattern is
  fixed (D83). Choice: keep the copy (parity) or fix it as NIKKE does.
- **D15 (a job's `notify` toggle)**: Rust copies Python: a change to a job's `notify` toggle reaches its runs
  only after a worker restart (enablement and cron are re-read). Choice: keep, or rebuild runners on change.
- **D53 (Stella Sora moved-file index)**: Rust copies Python's stale index entry after moving a file out of
  `disc/`, which would fail a run only for two titles differing in case and going to different folders (never
  seen on the wiki). Choice: keep or fix.
- **D19 / allocator**: jemalloc replaces Python's `malloc_trim`; chosen by measurement, listed so it is a known
  change in the image.
- **D182 is not a choice**: it is a defect to fix before Hanime1 runs on the Rust build.

## Open risks

1. **Hanime1 behind Cloudflare (D182)**: the Rust client was refused where Python's was accepted. Until the
   cause is found and fixed (request shape, header order, HTTP/1.1 details, or something not yet seen), Hanime1
   would stop working on the Rust build. Testing it needs a few live requests from the production network,
   ideally from the pod.
2. **Account-bound sources were never run live** (Bilibili, X, Pixiv, RedNote, WeChat, Telegram). Their
   behaviour rests on ported tests and fakes. Telegram in particular was verified under mocks only; grammers'
   behaviour against real Telegram (sessions, flood waits, file references) is untested.
3. **Stella Sora live untested**: the wiki's bot check blocks the sandbox for both builds; production reaches
   it today with Python, so the Rust request from production is the open question.
4. **Same TLS-fingerprint family of risk for other Cloudflare-fronted sites**: the plan noted reqwest/rustls vs
   httpx/OpenSSL. In the sandbox the egress proxy re-terminates TLS, so this was not measurable here; in
   production the site sees fav's own handshake. The client is built in one factory (`fav-net`), so the TLS
   backend can be swapped.
5. **Level 2 covered reads only**: write endpoints and MCP write tools are covered by level 1 tests, not by a
   replay against production data.
6. **BD2 and Nikke manifests** were compared through the API, not regenerated from data (they cannot be).
7. **Size**: 139k lines of Rust (about 90k outside test files) written by AI in one day, reviewed per package by
   an independent fresh session; the reviews kept finding real defects (two blockers, 61 should-fix), which
   suggests more remain in paths no test reaches.
