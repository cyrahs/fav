# Conventions for the Rust rewrite

Read with `PLAN.md`. These rules exist so that sessions that never met each other produce one code base,
and so that a reviewer can tell a faithful port from a plausible one.

## Ground rules

- Behaviour parity with the Python baseline (`rust/BASELINE`). Python bugs are copied and logged in
  `DIVERGENCES.md` unless they corrupt data; then fix them and log that too.
- The Python tree on this branch is the reference and the golden generator. Never edit anything outside
  `rust/`, `.github/workflows/rust.yml` and `.github/workflows/rust-image.yml`; `rust/tools/check_tree.sh` fails CI if you do. Never merge `main`
  into `rust`.
- Never deploy, never publish an image, never touch `charys117/nas-gitops`. Never point a Rust build at the
  production database, the production `collection/` volume or a real account. Account-bound sources are
  verified under mocks only (`PLAN.md`, hard safety rules).
- One work package = one thread = one PR from a branch off `rust`, into `rust`.
- Code, comments and docs in English (repository rule from `AGENTS.md`).

## Layout

```
rust/
  Cargo.toml            workspace, shared dependency versions and lints
  rust-toolchain.toml   pinned toolchain (1.97.0)
  BASELINE              the Python commit being ported
  crates/fav-core       env, settings, logging, filenames, Python-compatible JSON
  crates/fav-db         pool, consolidated schema, advisory locks
  crates/fav-net        HTTP client factory, streamed downloads, subprocess runner
  crates/fav-runtime    scheduler, control queue, notifications, source registry
  crates/fav-sources    one module per source
  crates/fav-browser    CDP driver, login window
  crates/fav-api        axum routes, MCP
  crates/fav            the binary
  goldens/              generated by tools/goldens; never edited by hand
  parity/               scope.toml (WP ownership of Python tests), waivers.toml, schema.txt (generated)
  tools/                goldens/, parity/, schema/, check_tree.sh, tests/ (self-tests of the tools)
  docs/                 PLAN, CONVENTIONS, PARITY (generated), DIVERGENCES, API-COVERAGE
```

A module mirrors the Python module it ports (`src/web/kemono.py` becomes `fav-sources/src/kemono.rs` or
`kemono/`), so a reviewer can put them side by side. Name the Python origin in the module doc comment.

## Code

- Edition 2024, toolchain from `rust-toolchain.toml`. Add dependencies to `[workspace.dependencies]` in
  `rust/Cargo.toml` and use `dep.workspace = true` in the crate; never two versions of one crate on purpose.
- Lints are workspace-wide (`[workspace.lints]`), CI runs clippy with `-D warnings`. `unsafe` is forbidden.
  `todo!()`, `unimplemented!()`, `dbg!()` are denied. No `#[ignore]` (checked by `check_tree.sh`). An
  `#[allow(...)]` needs a comment saying why.
- No placeholder implementations in merged code. If something cannot be ported yet, it is not merged; if it
  cannot be ported at all, it goes to `DIVERGENCES.md` with Max's decision.
- Errors: `thiserror` enums in library crates, `anyhow` only in the binary and tests. Error messages that
  Python surfaces to users (API `detail`, MCP tool errors, notification text) are copied verbatim.
- Logging through `fav_core::logging`: `let log = logging::get("jandan");` then `log.info(...)`,
  `log.notice(...)` and so on, which keeps Python's `embyx.<name>` logger names, the NOTICE level, `LOG_LEVEL`
  and the file format the MCP log tools parse. Other crates' `tracing` events from WARN up land in the same
  outputs. Tests read what was logged with `logging::capture`. Never log secrets (cookies, tokens, API
  hashes, proxy credentials, DSNs). Types holding one get a `Debug` that redacts it (see the settings
  models with `SENSITIVE_FIELDS`).
- Python-compatible data: `fav_core::pyjson` reads and writes JSON the way Python does (`1` and `1.0` stay
  apart, `json.dumps` byte formats), `fav_core::validate` reproduces pydantic's lax coercion and its error
  entries, `fav_core::pytext` has Python's `isspace`/`isdigit`/`strip`/`split`. Use them wherever Python's
  behaviour is observable (stored rows, API errors, filenames). For scraped pages (WP6):
  `fav_core::pyhtml` (CPython 3.12's `HTMLParser` tokenizer behind a handler trait, `html.unescape`), `pyurl`
  (`unquote`, `urlsplit`, `urljoin`), `pypath` (`PurePosixPath` joins, `name`, `suffix`, `stem`) and
  `pycasefold` (`str.casefold`). Python `re` patterns (WP8): `fav-sources/src/pyre.rs` compiles them as
  written, with `regex`, or `fancy-regex` where they need look-around or back-references, and rewrites `\s`
  to Python's class; see D73 for what is not translated.
- Database: `fav_db::Db` (pool and dedicated connections), `Db::ensure_schema` at startup (the only schema
  change mechanism: add tables, columns and indexes to `fav-db/src/schema.sql` in its three blocks, then
  regenerate the snapshot below), `Db::try_advisory_lock`, `Db::query_batch`/`insert_batch`, and
  `fav_db::SettingsStore` for `app_settings`. Write native PostgreSQL with `$n` placeholders.
- Test helpers live behind the `test-support` feature: `fav_core::golden` and `fav_db::testdb`. Add
  `fav-core = { workspace = true, features = ["test-support"] }` (or `fav-db`) to a crate's
  `[dev-dependencies]` to use them.
- `fav-runtime` has its own test helpers in `src/testutil.rs` (crate-private, `cfg(test)`): `database()`,
  `golden_json()`, and `FakeBotApi`, a local axum server that scripts Telegram Bot API answers and records
  every request (JSON or multipart). Telegram delivery is only ever tested against it, never the real bot.
- `fav-sources` has `src/testkit.rs` (crate-private, `cfg(test)`): `FakeServer`, a local axum server that
  answers every request through a closure and records it (httpx's `MockTransport`), and `RecordingNotifier`.
  Sources take a base URL override so tests point them at it.
- `fav-sources` has `src/testutil.rs` (crate-private, `cfg(test)`): `FakeWeb`, a local HTTP/1.1 proxy that
  every test client is pointed at (`ClientOptions::proxy`), so sources keep their real `http://` hosts; a
  handler returns `Reply::status`/`bytes`/`json`, `Reply::Close` (httpx's `RemoteProtocolError`) or
  `Reply::Stall` (a `ReadTimeout` with a short client timeout), and `seen()` records each request.
  Retry and pacing sleeps go through `fav_net::retry::Sleeper`; tests pass `RecordingSleeper` and assert
  the delays. A test that never touches the database can use `Db::connect_lazy` on an unreachable URL.
- Async tests that read `logging::capture` (thread-local) run on the current-thread runtime
  (`#[tokio::test]`) and poll the future inside the capture.
- All external effects are injected: HTTP client, database pool, clock, browser, Telegram client, subprocess
  runner, filesystem root. A source never builds its own client.
- Memory: stream downloads to `.part` and rename; stream large result sets; write manifests in batches; never
  hold a whole table in memory.
- `serde_json` with `preserve_order` (schemas and payloads keep key order). Python's `json.dumps` byte format,
  where stored data depends on it, goes through `fav-core`'s writer (WP1), never `serde_json::to_string`.
- Format with `cargo fmt` (`rustfmt.toml`: width 140).

## Tests

- Every Python test function is ported, or waived with a reason. Mark the Rust test with the Python id on the
  line(s) directly above its test attribute:

  ```rust
  // py: tests/test_kemono.py::test_parses_creator_page
  #[test]
  fn parses_creator_page() { ... }
  ```

  Stack several `// py:` lines when one Rust test covers several Python tests. Port the intent of the
  assertions, not the mocking mechanics, and never weaken an assertion: if Python checks an exact string,
  so does Rust.
- Scope: `rust/parity/scope.toml` says which work package owns which Python test (only `WP0`..`WP18`). If a
  package needs to split a file, add the more specific patterns there in its PR. Set the package's
  `status = "done"` in the PR that finishes it; CI then requires every test in scope to be ported or waived,
  and compares with the base branch so a done package can never be reopened or lose tests. When `WP18` is
  done, nothing may be pending anywhere.
- Waivers: `rust/parity/waivers.toml`, one entry per test with a reason that says why the behaviour does not
  exist in the Rust build (for example the SQLite-dialect translation layer). The independent review reads
  every waiver.
- `PARITY.md` is generated: run `python3 rust/tools/parity/parity.py --write` after changing claims, scope or
  waivers. CI fails on a stale file.
- Database tests run against real PostgreSQL, one temporary database per test, created through
  `FAV_TEST_DATABASE_URL` (CI: a PostgreSQL 17 service). Locally, start one from the PostgreSQL 16 binaries
  in `/usr/lib/postgresql/16/bin` or Docker. Tests that need it and do not find it fail; they do not skip.
- Chromium tests use `FAV_TEST_CHROMIUM` (CI sets it; cloud sessions fall back to `/opt/pw-browsers/chromium`).
- No test talks to the internet. HTTP is faked with a local server or an injected client.

## Goldens

- Goldens are deterministic outputs of the Python baseline, committed under `rust/goldens/<area>/`. They are
  produced only by `rust/tools/goldens/generate.py`; a porting session never writes expected values by hand.
  The generator refuses to run if `src` or any imported module (other than `areas/`) resolves under `rust/`.
  An area module must call the real Python code; one that returns literals defeats the check, and the
  independent review looks for exactly that.
- To add goldens, add or extend a module in `rust/tools/goldens/areas/` (`GOLDENS = {path: producer}`) that
  calls the real Python code, then run from the repository root:

  ```bash
  UV_PYTHON=3.12 uv run python rust/tools/goldens/generate.py          # writes rust/goldens/
  UV_PYTHON=3.12 uv run python rust/tools/goldens/generate.py --check  # what CI runs
  ```

  Use Python 3.12 (production's version); the repository's `.python-version` says 3.13, so set `UV_PYTHON`.
- Rust tests read goldens with `include_str!` or from `env!("CARGO_MANIFEST_DIR")/../../goldens/...` and
  compare byte for byte where the plan says so.
- Areas from WP0: `json` (every `json.dumps` format the code uses, `default=str` values, non-string keys and
  non-finite floats), `filename`,
  `db` (advisory lock ids), `scheduler` (APScheduler `from_crontab` next fire times, including its Monday=0
  weekdays and DST handling), `settings` (stored defaults, section registry), `jobs` (`JOB_SPECS`).
- Areas from WP1: `settings_validation` (`settings/validation.json`: every model with valid and invalid
  inputs and a coercion matrix, values or pydantic's error entries; `settings/build_settings.json`), `env`
  (environment and `.env` parsing), `text` (full code-point scans of `isspace` and `isdigit`),
  `logging_format` (file and console lines, level numbers).
- Areas from WP2: `scheduler` (more cron cases, including the DST repeats of D3), `notifications`
  (`render.json`: titles, bodies and payloads of every notification kind; `text.json`: `MarkdownV2` escaping
  and truncation; `send_message.json` and `deliver.json`: the Bot API requests Python's delivery makes for
  each scenario against a scripted fake API, and the resulting row), `site_sessions` (cookie codec,
  Netscape export), `jobs` (default jobs and `--trigger` target resolution). `mimetypes.guess_type` cases are
  generated with Python's built-in table only (`mimetypes._db = mimetypes.MimeTypes()`), so they do not
  depend on the generating machine's `/etc/mime.types`; Rust tests use `MimeTypes::defaults()` to match,
  while the binary uses `MimeTypes::system()`, which reads the same files Python does.
- Areas from WP6: `pyweb` (`html.unescape` and the HTML5 entity table, `HTMLParser` events over awkward
  markup, `unquote`/`urlsplit`/`urljoin`, `PurePosixPath` arithmetic, httpx's reason phrases and
  `raise_for_status` texts, `JSONDecodeError` texts), `stellasora` (title normalization, destination map, every page parser, API
  answers read through the real `resolve_files`), `pixiv` (bookmark, pages and ugoira payloads, extensions,
  user ids from the cookie, output paths). `fav-core/src/pyhtml/entities.rs` is generated by
  `rust/tools/codegen/html_entities.py` (`--check` compares); the `pyweb/entities.json` golden holds it to
  Python's table in the tests.
- Areas from WP5: `text` (`isdecimal.json`), `urls` (`urlsplit`/`urlunsplit`/`quote`/`unquote` and the
  `PurePosixPath` parts, `fav_core::pyurl` and `pypath`), `jandan` (AES `data` field both ways and Python's errors for malformed
  input, `zulu_to_offset` through `datetime.fromisoformat` including week dates and range errors, the JSON
  extractors and image URL helpers), `kemono` (`parse_post` on well-formed and malformed listings, file
  naming, URLs, `Retry-After`, `email.utils.parsedate_to_datetime`, `extract_kemono_creator`).
- Areas from WP8: `hanime1` (`t2s.json`: `opencc-python-reimplemented`'s `t2s` over every dictionary key and
  mixed strings; `t2s_dictionaries.json` pins the bundled dictionary files; `parsing.json`: every pure
  function of `src/web/hanime1.py`, `runtime_config.py` and `hanime1_author.py`, as `{fn, args, result}` with
  Python's exception class and message for a raise; `constants.json`). The replay test
  (`fav-sources/src/hanime1_golden.rs`) calls the Rust function of the same name for each case and fails on
  a name it does not know.
- Generate with the latest 3.12 patch release, as CI's `setup-python` does (`uv python install 3.12`; at
  WP5 that was 3.12.13). Older 3.12 patch releases differ in security fixes to `urllib.parse` and `email`,
  and an Ubuntu system 3.12.3 produces different goldens.

## Schema snapshot

`rust/parity/schema.txt` is what the Python baseline creates on an empty database: the generator calls every
`_ensure_table()`/`_ensure_schema()` through the real Python code against a temporary database and
describes the result with `rust/tools/schema/describe.sql` (one line per table, column, constraint, index).
`fav-db`'s schema test applies `schema.sql` to another temporary database and compares the same description.

```bash
FAV_TEST_DATABASE_URL=postgresql://tests@127.0.0.1:5432/fav-tests \
  UV_PYTHON=3.12 uv run python rust/tools/schema/dump_schema.py [--check]
```

## Before you push

```bash
cd rust
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cd ..
python3 rust/tools/parity/parity.py --write
UV_PYTHON=3.12 uv run python rust/tools/goldens/generate.py --check
FAV_TEST_DATABASE_URL=... UV_PYTHON=3.12 uv run python rust/tools/schema/dump_schema.py --check
rust/tools/check_tree.sh
```

Python tools follow the repository's ruff rules (`rust/tools/ruff.toml` extends `pyproject.toml`):
`UV_PYTHON=3.12 uv run ruff check rust/tools && UV_PYTHON=3.12 uv run ruff format --check rust/tools`.

## Definition of done for a work package PR

1. CI green: format, clippy, tests, tree check, goldens, schema snapshot, parity.
2. Every Python test in the package's scope ported or waived; `scope.toml` status set to `done`.
3. No placeholder implementations.
4. `PLAN.md` status table and experiment log updated; `DIVERGENCES.md` updated for every intentional
   difference.
5. An independent review by a fresh session against the Python source, looking for weakened assertions and
   missed behaviour. Its findings are posted on the PR and summarised in the experiment log.
